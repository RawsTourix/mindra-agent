# Документация MINDRA

## Назначение

Этот каталог — каноническая база знаний исследовательского проекта MINDRA.

Документация должна позволять человеку, ChatGPT, Codex или другому агенту разработки восстановить актуальный архитектурный контекст без необходимости опираться на историю отдельных чатов.

Краткое задание не заменяет документацию проекта.

# Основные уровни документации

```text
Концепция проекта
→ Архитектурная концепция
→ Исследовательская методология
→ Каноническая архитектурная семантика
→ ADR
→ Точные внутренние контракты
→ Проектирование версии
→ Последовательность реализации
→ Исследовательские результаты
```

Каждый уровень отвечает на свой тип вопросов.

### Концепция

Объясняет направление проекта, его предметную границу и главные идеи без точной реализации.

### Канонический design

Фиксирует принятые архитектурные семантики, зоны ответственности, invariants и взаимодействие подсистем.

### ADR

Фиксирует значимый выбор между несколькими реалистичными вариантами и его компромиссы.

### Точные внутренние контракты

Фиксируют точную форму уже принятой семантики: протоколы, поля, типы, lifecycle и другие интерфейсные детали.

### Проектирование версии

Определяет ограниченный scope конкретного этапа реализации и его prerequisites для приёмки.

### Исследовательские результаты

Фиксируют фактические эксперименты и результаты. Исследовательский результат не переписывает design напрямую: противоречащий результат инициирует пересмотр архитектуры.

# Иерархия решений

До появления более детальных документов действует общий порядок:

```text
принятый и не заменённый ADR + канонический Design
→ точный внутренний контракт
→ спецификация целевой версии
→ последовательность реализации
→ архитектурная концепция
→ концепция проекта
```

Более конкретный документ не должен молча отменять более фундаментальный invariant.

Если экспериментальные данные требуют изменить принятое решение:

```text
исследовательский результат
→ пересмотр архитектуры
→ ADR / обновление канонического design
→ согласованное обновление контрактов и версий
→ реализация
```

# Три разных вида истины

MINDRA строго различает:

```text
Design
Реализация
Исследовательские результаты
```

Документация не должна смешивать их.

Например:

- «Appraisal должен влиять на выбор действия» — архитектурное утверждение;
- «в текущем commit реализован `AppraisalModule`» — утверждение о реализации;
- «ablation снизил метрику на 8 ± 2 п.п.» — эмпирическое утверждение.

Ни один из этих тезисов сам по себе не доказывает наличие субъективного переживания.

# Язык

Документация и комментарии в коде пишутся на русском языке.

На английском остаются технические идентификаторы, имена типов, классов, функций, библиотек, API и термины, перевод которых ухудшает точность. Подробное правило: [`../AGENTS.md`](../AGENTS.md).

# Исследовательский журнал

Будущие гипотезы, протоколы экспериментов и результаты будут храниться отдельно в [`research/`](research/).

Это позволяет не смешивать каноническую архитектуру с фактическими исследовательскими данными.

---

# Текущий этап

На текущем этапе создаётся только фундамент документации.

Дорожная карта версий, точные контракты модулей, конкретные алгоритмы и стек реализации будут проектироваться отдельно после формирования достаточного канонического design.

Фактический статус: [`design/current.md`](design/current.md).
