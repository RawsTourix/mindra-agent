# Принципы проектирования MINDRA

## Статус документа

Этот документ фиксирует наиболее устойчивые инженерные и исследовательские принципы проекта.

Более конкретный design может уточнять их применение, но не должен молча им противоречить.

---

# 1. Архитектура важнее конкретной модели

MINDRA не является wrapper вокруг одной LLM.

Cortex backend должен рассматриваться как заменяемая capability внутри более широкой когнитивной архитектуры.

Выбор конкретной base model не должен определять всю структуру проекта.

---

# 2. Явная модульность

Каждый значимый компонент должен иметь понятные:

- responsibilities;
- inputs;
- outputs;
- owned state;
- dependencies;
- lifecycle;
- observability boundary.

Скрытые cross-module зависимости считаются архитектурным долгом.

---

# 3. Replaceability by contract

Заменяемость означает не только наличие интерфейса с одинаковым именем.

Компонент считается действительно заменяемым, если новая реализация может быть подключена без переписывания независимых потребителей и без нарушения зафиксированной семантики.

---

# 4. Диагностируемость обязательна

Исследовательский модуль должен быть спроектирован так, чтобы его вклад можно было проверить.

Где применимо, architecture должна позволять:

- отключить модуль;
- заменить его no-op/dummy/control реализацией;
- сохранить его входы/выходы;
- выполнить controlled intervention;
- повторить experiment из checkpoint/config.

---

# 5. Никаких скрытых магических механизмов

Если результат зависит от:

- heuristic;
- fallback;
- prompt injection внутреннего состояния;
- автоматической подмены модуля;
- скрытого дополнительного вызова Cortex;

это должно быть явной частью design и experiment record.

Нельзя создавать эффект, который невозможно отделить от самой исследуемой гипотезы.

---

# 6. Design ≠ implementation ≠ evidence

Эти три слоя никогда не смешиваются.

```text
Design intention
≠
Implemented mechanism
≠
Empirically demonstrated effect
```

Каждый сильный вывод должен указывать, к какому уровню он относится.

---

# 7. Functional claims before anthropomorphic claims

MINDRA описывает механизмы через функционально проверяемые свойства.

Предпочтительная формулировка:

> изменение internal state причинно увеличивает вероятность exploration.

Непредпочтительная без отдельного основания:

> агент заинтересовался.

Антропоморфная терминология может использоваться как короткая рабочая аналогия, но не как доказательный вывод.

---

# 8. Один механизм — одна понятная ответственность

Не следует создавать универсальный `CognitiveManager`, который одновременно:

- управляет памятью;
- считает utility;
- формирует goals;
- вызывает Cortex;
- выбирает action;
- обновляет training state.

Границы должны соответствовать различимым исследовательским функциям.

---

# 9. Каноническое внутреннее взаимодействие

Модули должны обмениваться данными через явно спроектированные contracts/state boundaries.

Model-specific tensors или private implementation objects не должны без необходимости протекать через всю систему.

Точная форма canonical state representation будет определена позднее.

---

# 10. Наблюдаемость без вмешательства по умолчанию

Логирование и instrumentation должны позволять исследовать систему, не меняя существенно её поведение.

Если наблюдение само влияет на training/runtime semantics, это должно быть явно зафиксировано.

---

# 11. Воспроизводимость как часть архитектуры

Experiment identity, configuration, seeds, code version и checkpoints не являются второстепенной отчётностью.

Система должна проектироваться так, чтобы meaningful run можно было восстановить настолько полно, насколько это practically возможно.

---

# 12. Determinism where possible

Не все GPU/ML операции полностью детерминированы, но случайность должна быть управляемой.

Нужно различать:

- ожидаемую стохастичность алгоритма;
- uncontrolled nondeterminism;
- ошибку воспроизводимости.

Точная seed/determinism policy будет определена в соответствующем design.

---

# 13. Минимизация confounding variables

При проверке нового механизма остальные условия должны изменяться как можно меньше.

Нельзя считать semantic module полезным только потому, что вместе с ним выросли:

- parameter count;
- prompt length;
- training budget;
- number of Cortex calls;
- memory capacity;
- compute.

---

# 14. Не усложнять без evidence

MINDRA может быть сложной архитектурой, но сложность сама по себе не является целью.

Если модуль:

- не даёт измеримого эффекта;
- дублирует другой механизм;
- не поддаётся диагностике;
- создаёт больше confounders, чем пользы,

его наличие должно быть пересмотрено.

---

# 15. Никакого premature end-to-end

Не предполагается, что вся система должна сразу обучаться end-to-end.

На ранних этапах предпочтительно изолированно проверять механизмы и их contracts, если это уменьшает неопределённость и улучшает интерпретируемость результата.

Точный training strategy будет определён отдельным design.

---

# 16. Кандидат не равен решению

Обсуждавшаяся технология остаётся кандидатом, пока не зафиксирована в canonical design или accepted ADR.

Это относится в том числе к:

- base models;
- RL algorithms;
- state frameworks;
- vector stores;
- memory implementations;
- training libraries;
- compute platforms.

---

# 17. Documentation-first для существенных решений

Значимое изменение границ, semantics или research methodology должно сначала появиться в design/ADR, а затем в коде.

Небольшие implementation details, не создающие нового контракта и не влияющие на исследовательскую валидность, не требуют отдельного ADR.

---

# 18. Версии после архитектурного design

Version roadmap не должен использоваться для преждевременного разбиения ещё не спроектированной архитектуры.

Сначала формируются достаточные canonical design и dependencies, затем из них выводится реалистичная последовательность implementation milestones.

---

# 19. Отрицательный результат допустим

Архитектура не обязана подтверждать первоначальную идею.

Если experiment опровергает гипотезу, правильный результат — изменить понимание проекта, а не подогнать metric или interpretation.

---

# 20. Исследовательская честность важнее красивой narrative

История MINDRA должна сохранять:

- rejected alternatives;
- superseded decisions;
- отрицательные результаты;
- известные ограничения;
- unresolved questions.

Это часть ценности исследовательского проекта.
